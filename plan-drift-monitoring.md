# Plan: DriftWatch production drift detection

## Goal

Add scheduled, batch-based model monitoring for the tennis prediction model using **DriftWatch** and **Prefect**. Each monitoring run will compare newly available, labeled match outcomes against the model's recorded predictions and the training reference data.

## Scope

### In scope

- DriftWatch as the only drift-detection library.
- A scheduled Prefect monitoring flow.
- Delayed-label evaluation after new match results arrive.
- Feature, prediction, and performance/concept drift reports.
- Aggregate monitoring metrics logged to MLflow.
- Persisted monitoring results for historical review and alerting.
- Segment-level checks for surface and tournament level when sample sizes permit.

### Out of scope

- Canary-ml, Evidently, Alibi Detect, or another monitoring framework.
- BentoML middleware or request interception.
- Per-request logging inside `src/serving/service.py`.
- Automatic retraining, model promotion, rollback, or deployment.
- Treating unlabeled prediction logs as accuracy measurements.

## Required data contract

The monitoring flow must receive a persisted prediction dataset from the existing prediction caller or batch process. The plan does not add BentoML middleware.

Each prediction record must contain:

- `match_id` — stable join key.
- `model_version` — resolved MLflow model identity, preferably the champion version.
- `predicted_at` — timestamp before the match result was known.
- `p_win` — probability that the canonical `player_id` wins.
- Canonical player/opponent IDs and the feature columns used by the model, or a reference to the feature row.

The existing match data provides the delayed label:

- `gold.match_features.match_id` joins the prediction to the match.
- The canonical target is derived from the existing winner/canonical orientation.
- Only predictions whose match result is now available and whose `predicted_at` precedes the match result are eligible for performance evaluation.

If production prediction records are not available, the flow may report feature/prediction distribution drift only; it must not claim production accuracy.

## Tasks

### [ ] Task 1: Define the prediction and monitoring datasets

- **Description**: Establish the persisted input contract for predictions and the output contract for monitoring runs. Store one immutable prediction record per `match_id` and `model_version`; make reruns idempotent.
- **Files**: `src/constants.py`, `dbt/models/gold/` (new monitoring source/model as appropriate), `tests/` (new focused contract tests).
- **Acceptance Criteria**:
  - A prediction can be joined to exactly one match result by `match_id`.
  - Duplicate prediction records are rejected or deterministically deduplicated.
  - A label is generated using the repository's canonical lower-ATP-ID orientation.
  - Unlabeled and post-result predictions are excluded from accuracy calculations.
- **Guardrails**: Do not log request bodies in BentoML middleware. Do not recompute predictions from post-match features when an original production prediction is unavailable and call it production performance.

### [ ] Task 2: Establish DriftWatch reference data

- **Description**: Build the stable reference dataset from the training/evaluation window used for the promoted model. Persist the feature column order, categorical handling, model version, and reference predictions required by DriftWatch.
- **Files**: `src/features/columns.py`, `notebooks/parameters/01_train_test_split.ipynb`, `notebooks/parameters/05_evaluate.ipynb`, `src/constants.py`.
- **Acceptance Criteria**:
  - Reference features use the same `FEATURE_COLS` order as serving/training.
  - Reference predictions are generated by the exact promoted model version being monitored.
  - The reference window and model version are recorded and reproducible.
  - Missing values and categorical fields use the same preprocessing assumptions as production.
- **Guardrails**: Do not use the entire historical table as an unqualified baseline if the promoted model was trained on a narrower time window. Do not include the target label as a feature.

### [ ] Task 3: Add the scheduled Prefect drift-monitoring flow

- **Description**: Add a separate flow that runs after ETL has incorporated new match results. It loads newly labeled prediction records, joins labels, creates the current monitoring batch, invokes DriftWatch, and persists the report.
- **Files**: `src/flows/drift_monitor.py` (new), `src/flows/etl.py`, `src/constants.py`, `tests/` (new flow/unit tests).
- **Acceptance Criteria**:
  - The flow can run on a schedule and can also be invoked manually for a date range.
  - It processes only new, eligible labeled predictions since the last successful run.
  - Empty batches complete successfully without producing false drift alerts.
  - Re-running the same date range does not duplicate monitoring results.
  - DriftWatch receives production features, production predictions, and true labels separately and uses the correct API for feature, prediction, and concept/performance checks.
  - The flow records the monitored `model_version`, reference window, production window, row count, and DriftWatch package/configuration version.
- **Guardrails**: Prefect owns scheduling and orchestration; do not add a second scheduler, API middleware, or background monitoring thread.

### [ ] Task 4: Compute labeled performance and drift metrics

- **Description**: Use DriftWatch for the statistical checks and calculate the model metrics needed for an actionable production report. For this binary probability model, include log loss, Brier score, accuracy at the chosen threshold, calibration, sample count, and per-segment results where sample sizes are sufficient.
- **Files**: `src/flows/drift_monitor.py`, `dbt/models/gold/` (monitoring result model), `tests/` (metric and edge-case tests).
- **Acceptance Criteria**:
  - Performance metrics are calculated only from joined ground-truth labels.
  - The report distinguishes feature drift, prediction drift, and performance/concept drift.
  - Metrics are reported globally and, when statistically valid, by surface and tournament level.
  - Small segments are marked insufficient rather than generating unreliable alerts.
  - Thresholds are configuration values recorded with each run, not hidden constants.
- **Guardrails**: Do not use prediction-distribution drift as a substitute for accuracy. Do not trigger retraining solely from one noisy segment or one statistical test without the agreed aggregation rule.

### [ ] Task 5: Log aggregate monitoring runs to MLflow

- **Description**: Log one MLflow run per monitoring window, linked to the monitored model version. Log aggregate metrics, parameters, and a compact report artifact—not every prediction row.
- **Files**: `src/flows/drift_monitor.py`, `src/constants.py`, `tests/` (MLflow logging contract test if the repository's test setup supports it).
- **Acceptance Criteria**:
  - Each run includes the model version/alias, production date window, reference window, row counts, and label coverage.
  - Aggregate metrics include log loss, Brier score, accuracy, calibration error, DriftWatch feature/prediction/concept drift status, and counts of affected features/segments.
  - The full JSON/HTML DriftWatch report is stored as an MLflow artifact or durable monitoring artifact.
  - MLflow logging failures are visible and do not silently mark a monitoring run as healthy.
- **Guardrails**: Do not store raw prediction rows or player-sensitive payloads as MLflow parameters or metrics. MLflow is for model-linked monitoring history and comparison, not the primary prediction database.

### [ ] Task 6: Add alerting and operational status

- **Description**: Define the alert policy for the Prefect flow and surface failed monitoring runs separately from detected model drift. Alerts should identify the model version, window, affected drift type, sample size, and recommended next action.
- **Files**: `src/flows/drift_monitor.py`, existing Prefect deployment configuration, `tests/` (alert-policy tests).
- **Acceptance Criteria**:
  - A failed flow, an empty/late-label batch, and a drift detection are distinguishable states.
  - Alerts include enough context to investigate the affected feature/segment and compare against recent runs.
  - Repeated alerts are deduplicated or rate-limited by monitoring window/model version.
  - No automatic retraining or deployment occurs as a side effect.
- **Guardrails**: Do not page on unlabeled data alone. Do not make a promotion decision from drift metrics without a separate evaluation gate.

## Dependencies

1. DriftWatch version and exact `.check()` contract must be pinned and verified against the chosen task type.
2. Production prediction records with stable `match_id` must exist outside BentoML middleware.
3. ETL must finish loading new match results before the monitoring flow runs.
4. The monitoring process must resolve the exact MLflow champion/model version being evaluated.
5. A notification destination and initial thresholds must be selected.

## MLflow purpose

MLflow does not make DriftWatch more accurate and should not be used as the row-level event store. Its value is longitudinal comparison:

- See whether the current champion's log loss or calibration worsens over time.
- Compare monitoring windows across model versions.
- Preserve the reference window and monitoring configuration used for each result.
- Keep drift reports alongside the model identity that produced the predictions.
- Support later retraining and promotion decisions with an auditable history.

## QA/Testing Scenarios

- A new labeled batch with no drift produces a successful, non-alerting run.
- A shifted feature distribution is reported as feature drift.
- A changed prediction distribution is reported as prediction drift.
- Deliberately inverted or degraded predictions produce worse log loss/Brier score and performance drift.
- Predictions with missing or unmatched labels are excluded and counted.
- Duplicate `match_id` records do not double-count performance metrics.
- A batch below the minimum sample size produces an insufficient-data status, not an alert.
- The same monitoring window can be rerun idempotently.
- A changed champion model version creates a separate monitoring lineage.
- MLflow receives aggregate metrics and a report artifact without raw prediction payloads.
